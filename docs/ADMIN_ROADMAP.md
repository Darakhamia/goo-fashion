## Как читать

- ID задач — `GS<этап>-<номер>` (goo-studio). Так они не путаются с `Б*` из плана аудита и с `А*`, `С*`, `Д*`, `М*` из `docs/UX_REVIEW_2026-09.md`.
- Оценки: **S** — до 2 ч, **M** — от полудня до дня, **L** — 2+ дня, на одного фуллстека.
- У задачи есть: что делать, где в коде, DoD (как понять, что готово), зависимости и риски.
- Протокол тот же, что у плана аудита (`AUDIT_PLAN_BRIEF.md`):
  - перед правкой перепроверить, что проблема ещё на месте;
  - одна задача — один коммит, ID в первой строке сообщения;
  - DoD проверяется фактическим прогоном.
  - Миграции на проде, массовые правки данных и рассылки — только после подтверждения CEO.
- UI-правки — по `DESIGN_SYSTEM.md` §9 и чеклисту §10. Где задача меняет сам §9, это помечено: такая правка требует решения CEO.

## Главное за минуту

1. **Три вещи в админке выключены, и кодом их не включить.** Cron продления не заведён, 12 миграций не применены. Нужен доступ к Coolify и базе — это этап 0.
2. **На этапе 0 две ловушки:**
   - **Миграции — только недостающие и по одной.** `007_embeddings_openai_1536.sql:12` делает `drop column if exists embedding`. Повторный прогон папки целиком сотрёт 284 готовых embeddings.
   - **Перед миграцией `025` переключить AI check с `auto` на `suggest`** (`catalogue-check/store.ts:73`). Сразу после миграции фоновая проверка начнёт сама править непроверенный каталог: она запускается после каждого импорта и при заходе на страницу AI check, в пределах $5 в месяц.
3. **Самый вредный дефект в данных — бренд.** Дефолтного бренда в коде нет. Импорт оставляет любой бренд, который уже встречался в каталоге, даже если название товара говорит другое (`parser/brand-from-name.ts:247-248`). А список «известных» брендов строится из самого каталога. Ошибка, попав один раз, воспроизводит себя.
4. **Audit советует чушь из-за формулы, а не из-за шума.** Правила сортируются по уверенности без учёта объёма (`mining.ts:199-205`, правило на 4 товарах против правила на сотнях):

   | Правило | Совпадений | Уверенность | Итог |
   |---|---|---|---|
   | «silicone → Watches» | 4 из 4 | 100% | срабатывает первым |
   | «tee → Tees» | сотни | 97% | проигрывает |

   Чинится за день и снимает большую часть из 104 открытых замечаний.
5. **Аналитика хуже, чем видно.** Из 17 событий, объявленных в коде, реально отправляются только 3. Пометку «not tracked» носят три карточки, остальные молча показывают 0.
6. **У рассылок нет ни согласия, ни отписки, ни заголовка `List-Unsubscribe`.** Команда входит в аудиторию «All users». Пока CEO не решил вопрос согласия, маркетинговые рассылки лучше не отправлять.
7. **Дизайн:** основа хорошая, переделывать стиль не нужно. Не хватает иерархии, плотности и контраста:
   - капс на всём;
   - карточки темнее фона;
   - метаданные и статусы ниже порога AA;
   - Audit и Duplicates — страницы по 10 000px.

   Плюс 11 визуальных багов (`docs/ADMIN_DESIGN.md`, раздел 1). Один из них серьёзный: в редакторе товара не видна цена магазина. Он идёт первым — GS1-0.

## Что ревью увидело не так

Ревью смотрело живую админку, сверка — код. Расхождения меняют задачи, поэтому они собраны здесь.

1. **Массовые операции в Products уже спрашивают подтверждение.** Перед действием идёт пробный прогон, потом `confirm` с числом товаров (`products/page.tsx:1425, 1454, 1501, 1537, 1621, 1710`). Не хватает другого: эти кнопки стоят в одном ряду с `Add product`.
2. **Цену товара вручную не правят и не теряют.** Когда у товара есть цены магазинов, поля цены `readOnly` и полупрозрачные (`products/page.tsx:2972, 2984`). При сохранении цена пересчитывается из магазинов (`:932-936, :1101`). Проблема в подаче: поле выглядит почти как обычное. Цену можно поправить только через цену магазина — см. развилку Р8.
3. **Кнопки AI check без миграции 025 уже выключены** (`catalogue-check/page.tsx:320`), но:
   - они выглядят активными: у выключенной кнопки только 40% прозрачности;
   - «1224» в надписи — это все товары, а не непроверенные;
   - умолчание режима `auto` опасно после миграции (GS0-3).
4. **У рассылки подтверждение есть.** Кнопка превращается в «Confirm send» (`email/page.tsx:469-500`). Но она стоит вплотную к «Send test to me», и модалки нет.
5. **Categories.** Группу с товарами удалить нельзя (`api/categories/route.ts:413-428`). Подкатегорию — можно: подтверждение показывает число товаров, у товаров подкатегория обнуляется, сами товары не удаляются (`:462-472`). Переноса в другую подкатегорию нет.
6. **Embeddings сейчас ни на что не влияют.** Семантический поиск стилиста включается только переменной `STYLIST_SEMANTIC_SEARCH` (`api/stylist/chat/route.ts:24-25`). По решению CEO из код-ревью сентября её не включали. Покрытие 23% станет проблемой в момент включения флага (Р13).
7. **«Air Jordan» — не бренд по умолчанию.** Дефолтного бренда нет; причины разобраны в GS2-1.
8. **Ошибка с полом — не «homme» внутри «femme».** Аудит вызывает старую `inferGenderFromText` (`product-fields.ts:783-790`). Она ищет женские слова первыми, по названию **и описанию**, без границ слов. Новая `genderFromPage()` (`taxonomy/gender.ts:20-22`) эту ошибку уже исправляет: импорт на неё переведён, аудит и подсказки полей — нет.
9. **Повторы в фильтре Activity — не регистр и не пробелы.** Список строится по `admin_id`. Одна почта дважды означает два разных аккаунта Clerk с этой почтой — скорее всего, dev- и prod-инстанс (`MIGRATION_RUNBOOK.md:96`). Проверяется SQL-запросом в GS6-8.
10. **В аналитике не отслеживаются 14 событий из 17, а не 3.** Пометка стоит только на трёх (`api/admin/analytics/route.ts:158`).
11. **Курс 41 вбит не намертво.** Это запасное значение переменной `BILLING_USD_UAH_RATE` (`lib/plans.ts:100`).
12. **Меню уже умеет группы** (`layout.tsx:21-29`). Перестройка — это правка поля `category` у пунктов. Сохранённый порядок пунктов живёт в `localStorage`, перестройка его не сломает.
13. **«12 missing» в Settings.** Проверка схемы смотрит:
    - 13 пар таблица/колонка;
    - 17 необязательных колонок товаров.

    Корневые `supabase-migration-*.sql` (подписки, `billing_events`, user-data, логотипы брендов) она не проверяет вообще. Товары при отсутствующих колонках сохраняются: колонки отбрасываются с предупреждением (`lib/data/db.ts:196-207`). Тихой потери нет, но GTIN/MPN/SKU не пишутся.
14. **`role="dialog"` нет только у четырёх модалок Products.** У остальных модалок админки роли есть.
15. **Круговые диаграммы в Analytics — 100×100 px.** Огромные там карточки вокруг них, а не сами диаграммы.

### GS0-3. AI check: умолчание `suggest` вместо `auto` · S, код
**Что:** `DEFAULT_CHECK_SETTINGS.mode` → `"suggest"`.

### GS0-5. Миграции применяются сами при старте приложения · M
**Зачем:** сейчас каждую миграцию прогоняют руками в SQL-редакторе Supabase. Её легко пропустить или прогнать лишнюю — `007` стирает embeddings.

**Что делать:**
1. **Скрипт `scripts/migrate.mjs`** на пакете `pg`:
   - таблица `schema_migrations (name text primary key, applied_at timestamptz default now())`;
   - `pg_advisory_lock`, чтобы два экземпляра приложения не применяли одно и то же;
   - файлы из `supabase/migrations` по порядку имён, только те, которых нет в таблице, каждый в своей транзакции;
   - на первой ошибке — стоп, ошибка в лог и в Settings → Database schema. Приложение всё равно стартует: оно переживает отсутствующие колонки.

4. **`package.json`:** `"start": "node scripts/migrate.mjs && next start …"`. Без `DATABASE_URL` скрипт пишет предупреждение и выходит с кодом 0 — старт не блокируется ни в каком случае.
5. **Settings → Database schema:**
