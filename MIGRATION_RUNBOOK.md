## 1. Что выяснилось до начала работ

### 1.1. Сайт действительно живёт на старом сервере, не на Vercel **[проверено]**

```
goo-fashion.com       A -> 65.108.92.69
www.goo-fashion.com   A -> 65.108.92.69
curl -I https://goo-fashion.com -> HTTP/2 200, x-powered-by: Next.js,
                                   x-nextjs-prerender: 1, alt-svc: h3
```

Заголовков `x-vercel-id` / `server: Vercel` нет — отдаёт Traefik старого сервера.

Это важно, потому что **документация в репозитории говорит обратное**: `README.md`
(«Hosting: Vercel»), `BILLING.md` («Deploy to Vercel»), комментарии в
`src/proxy.ts` («behind Vercel's proxy»), `vercel.json` с cron-расписанием и
записи аудита от 7 августа про «переменные окружения Vercel». Опираться на эти
файлы при миграции нельзя — они описывают прошлый хостинг.

### 1.2. GOO Fashion работает на self-hosted Supabase — он переезжает вместе с ним **[проверено]**

Это главный вопрос исходного runbook («используется ли self-hosted Supabase
вообще?»), и ответ — да, используется, целиком.

```
supabase.goo-fashion.com  A -> 65.108.92.69
curl -I https://supabase.goo-fashion.com/storage/v1/object/public/generated-outfits/...
   -> HTTP/2 200, server: kong/3.9.1, last-modified: Sat, 01 Aug 2026
```

Kong 3.9.1 — это API-шлюз Supabase. На одной только главной странице 125 ссылок
на картинки с этого хоста; в каталоге (`/api/products`, 516 товаров, 2130 ссылок
на изображения) — 941 ссылка.

**Ветка исходного runbook «если `numbackends` 0–1, снести стек и вернуть 2.65 GiB»
закрыта.** Стек — это база и файловое хранилище GOO Fashion. Освободить память на
старом сервере можно только после того, как Supabase уедет на новый.

### 1.3. У приложения нет собственной базы **[проверено]**

В `package.json` нет ни `pg`, ни Prisma, ни Drizzle; в коде нет `DATABASE_URL`.
Единственный способ, которым приложение ходит в данные, — HTTPS через
`@supabase/supabase-js` (`src/lib/supabase.ts`), то есть PostgREST на
`SUPABASE_URL`.

Следствия:
- «Перенести базу приложения» из этапа 6 исходника относится к **постгресу внутри
  Supabase**, а не к отдельному контейнеру приложения.
- Неопознанные `postgres:16-alpine` из инвентаризации (`nm5ovx53…` и остальные)
  к GOO Fashion отношения не имеют — трогать их в рамках этой миграции нечего.
- `DATABASE_URL=postgresql://user:pass@10.0.0.X:5432/…` из этапа 7 исходника
  приложению задавать не нужно: такой переменной оно не читает.

### 1.4. Приложению не нужен persistent volume **[проверено]**

Единственная запись на локальный диск во всём коде — кеш fontconfig в `tmpdir()`
(`src/lib/server/card-image.ts:102`), он одноразовый. Всё остальное состояние — в
Supabase. Пункт «перенести persistent volumes приложения» из этапа 7 исходника
можно вычеркнуть (но подтвердить `docker inspect` при инвентаризации — вдруг том
подмонтирован по другой причине).

Реальный том, который надо перенести, — **том Storage внутри Supabase**.

### 1.5. Что именно приложение берёт от Supabase **[проверено]**

| Компонент Supabase | Использует ли GOO Fashion | Чем подтверждено |
|---|---|---|
| PostgREST (`/rest/v1`) | да, основной способ доступа | `src/lib/supabase.ts`, все `.from(...)` |
| Storage (`/storage/v1`) | да, 4 бакета | `product-images`, `generated-outfits`, `site-assets`, `outfit-images` |
| SQL-функции | да, три | `match_products` (pgvector), `search_products` (FTS), `run_sql` |
| GoTrue (`/auth/v1`) | **нет** | авторизация — Clerk (`pk_live`, `clerk.goo-fashion.com`) |
| Realtime | нет | ни одного `.channel(` в коде |
| Edge Functions | нет | ни одного `functions.invoke` |
| imgproxy / трансформации | нет | `getPublicUrl` без `transform:` |
| Supavisor (пулер) | нет | прямых подключений к постгресу нет |

Обновление 26.09.2026: `run_sql` код больше не вызывает (DDL для `crop_data` и
`settings` вынесен в миграции 023 и 024, этап 6.5). Используются две функции:
`match_products` и `search_products`.

Из этого следует **решение, которое стоит принять до заказа сервера** (см. §3):
на новом сервере можно поднять не весь шаблон Supabase на 14 контейнеров, а
db + kong + rest + storage (+ studio/meta для SQL-редактора). Это разница между
~2.65 GiB и примерно 1 GiB, и она напрямую влияет на тариф.

### 1.6. Ссылки на картинки хранятся в базе абсолютными — домен менять нельзя **[проверено]**

`uploadToStorage` возвращает `getPublicUrl(...)`, и в базу ложится полный URL
вида `https://supabase.goo-fashion.com/storage/v1/object/public/product-images/…`.
Таких ссылок только в каталоге 941, плюс образы луков, обложки блога, логотипы.

**Значит, `supabase.goo-fashion.com` должен переехать как имя.** На новом сервере
Supabase поднимается под тем же доменом, а переключение — это перевод A-записи,
ровно как для основного домена. Любой другой хост потребует переписывания всех
URL в базе, и это будет отдельная миграция данных с отдельным риском.

Хорошая новость: `*.supabase.co` в данных не встречается ни разу — старого
облачного проекта в каталоге не осталось, переписывать нечего.

### 1.7. Объём данных **[проверено, кроме размера тома]**

- 516 товаров, 10 луков, 9 постов блога (по `sitemap.xml`: 545 URL).
- 941 файл-ссылка на своё хранилище; выборка из 12 файлов дала средний размер
  **203 KiB**. Порядок величины бакета `product-images` — сотни мегабайт, не
  десятки гигабайт.
- Точный размер снять на сервере **[нужен доступ к серверу]**:
  `du -sh /var/lib/docker/volumes/*storage*/_data`.

То есть перенос файлов — это минуты, а не ночь. Это заметно снижает риск всей
операции по сравнению с тем, как её оценивал исходный runbook.

### 1.8. Остальное окружение — внешние сервисы, переносить нечего **[проверено]**

Clerk (`clerk.goo-fashion.com`, `accounts.goo-fashion.com` → CNAME на Cloudflare),
Upstash Redis, monobank, OpenAI, Replicate, Resend, PostHog. При смене
A-записей их не трогать. (Обновление 26.09.2026: Anthropic больше не используется —
SDK удалён из кода.)

### 1.9. `plane.goo-fashion.com` мёртв — и приложение об этом не знает **[проверено]**

```
plane.goo-fashion.com -> NXDOMAIN (A-записи нет вообще)
```

При этом `src/app/api/report-bug/route.ts:124` до сих пор POST-ит баг-репорты в
`https://plane.goo-fashion.com/api/v1/...`, а `/report` показывает на него ссылку.
Сегодня любой отправленный через форму баг-репорт заканчивается 500-й (после
оплаченного вызова Claude API на разбор текста).

Для миграции: переносить нечего, поддомена нет. Отдельной задачей — либо поднять
Plane заново, либо убрать интеграцию.

Обновление 26.09.2026: текст баг-репорта теперь разбирает OpenAI (`gpt-4o-mini`), а
не Claude, но POST в Plane остался (`src/app/api/report-bug/route.ts`), так что
итог тот же — 500 после оплаченного вызова модели.

## 2. Найденное попутно, к миграции не относится

Фиксирую, чтобы не потерялось. **Чинить не в этой работе** — по протоколу
`AUDIT_PLAN_BRIEF.md` это решения CEO.

1. **Оптимизатор картинок отключён для собственных изображений.**
   `next.config.ts` разрешает `*.supabase.co`, а прод отдаёт с
   `supabase.goo-fashion.com`; та же регулярка в `src/lib/image.ts:32`
   (`OWN_IMAGE_HOSTNAME`). Итог: на главной **ноль** обращений к `/_next/image`,
   а принудительный вызов
   `/_next/image?url=https://supabase.goo-fashion.com/...` отдаёт **400**.
   Все свои фото уходят в браузер в оригинальном размере, без WebP/AVIF.
   Прямо связано с Б0-3 из плана аудита.
2. **Каталог почти не зеркалирован.** Из 2130 ссылок на изображения 1189 всё ещё
   ведут на CDN ритейлеров (Farfetch 712, productserve 320, Shopify 153) — то
   самое хотлинкание, против которого написан `product-images.ts`. Это источник
   429-х из аудита.
3. **Автопродление подписок под вопросом.** Расписание объявлено в `vercel.json`,
   а прод не на Vercel. Cron работает только если (а) в Coolify заведён Scheduled
   Task на `GET /api/billing/cron/renew` с заголовком `Authorization: Bearer
   $CRON_SECRET`, либо (б) в Vercel до сих пор жив деплой этого репозитория.
   Вариант (б) хуже, чем кажется: это второе приложение, пишущее в ту же базу, и
   при миграции о нём легко забыть. Проверить оба — см. этап 1.
   Обновление 26.09.2026: целевой вариант — (а), Scheduled Task в Coolify (этап 7,
   п.5, подробно — `BILLING.md`). Работает ли cron сейчас, видно без SQL:
   `/goo-studio/subscriptions` → карточка «Renewal cron» и плашка вверху страницы,
   если последнего прогона нет или он был 36 ч назад и раньше.
4. **`NEXT_PUBLIC_SITE_URL`.** В `.env.example` стоит `https://www.goo-fashion.com`,
   а `src/proxy.ts` отвечает на www редиректом 308 на апекс. Из этой переменной
   строится `webHookUrl` для monobank (`checkout/route.ts:53`). Если в проде
   задан www — вебхуки об оплате прилетают на редирект. Проверить фактическое
   значение при выгрузке переменных.
   Обновление 26.09.2026: пример в `.env.example` исправлен на апекс, без www;
   значение на проде это не меняет — сверить его всё равно.

## 3. Пересчёт: какой сервер нужен

Исходный runbook давал вилку «без Supabase — CX32, с Supabase — CX42 и выше».
Supabase едет (§1.2), но объём меньше, чем выглядел, потому что половина стека
приложению не нужна (§1.5).

| Что | Полный шаблон Supabase | Урезанный стек |
|---|---|---|
| Supabase | ~2.65 GiB | ~1.0–1.3 GiB (db + kong + rest + storage) |
| Next.js в рантайме | ~0.5 GiB | ~0.5 GiB |
| Coolify + Traefik | ~0.7 GiB | ~0.7 GiB |
| Пик сборки `next build` | ~2.0 GiB | ~2.0 GiB (или 0, если собирать в CI) |
| ОС и кеш | ~0.5 GiB | ~0.5 GiB |
| **Итого пик** | **~6.4 GiB** | **~4.7 GiB** (или ~2.7 GiB без сборки на сервере) |

Про пик сборки — цифра не с потолка: `nixpacks.toml` ограничивает V8 в 3072 MB и
в комментарии фиксирует замеренный пик ~1.9 GB по всем node-процессам.

**Рекомендация:** CX32 (4 vCPU / 8 GB) + 8 GB свопа + memory limits на контейнеры.
При полном шаблоне Supabase 8 GB — это впритык в момент сборки, поэтому здесь же
второй рычаг: в репозитории уже есть `.github/workflows/ci.yml`, который на каждый
PR выполняет `npm run build` на раннерах GitHub. Перенести туда же сборку образа —
работа на пару часов, и тогда пик со сборкой с сервера уходит совсем.

CX42 (8 vCPU / 16 GB) — вариант «не думать»: полный шаблон Supabase, сборка на
сервере, запас на рост каталога. Разница в цене за год заметная.

**Цены не привожу принципиально** — по правилу исходного runbook их проверяет
David в Hetzner Console на момент заказа.

Диск: 80 GB (CX32) хватает с запасом — образы Supabase ~4 GB, данные <1 GB.

**Решение за CEO:** CX32 + урезанный Supabase + сборка в GitHub Actions (дешевле,
но три дополнительные настройки) против CX42 + всё как есть (дороже, проще).

## 4. Этапы

Нумерация сохранена от исходного runbook, чтобы можно было сверять.

### Этап 0 — стабилизация старого сервера (делать первым)

Без изменений относительно исходника: своп 8 GB, `vm.swappiness=10`, ротация
docker-логов. Одно уточнение: **перезапуск docker ради ротации логов можно не
делать сейчас**. Настройка в `daemon.json` применяется только к вновь создаваемым
контейнерам, поэтому она всё равно не подчистит уже распухшие логи. Если диск
жмёт прямо сейчас, быстрее и без даунтайма:

```bash
# сначала посмотреть, кто именно распух
du -sh /var/lib/docker/containers/*/*-json.log | sort -h | tail -10
# и только потом обнулить конкретные (truncate, не rm — файл открыт демоном)
truncate -s 0 /var/lib/docker/containers/<id>/<id>-json.log
```

`daemon.json` при этом написать, а `systemctl restart docker` отложить до
ближайшего окна — или вообще до момента, когда GOO Fashion уже уедет и даунтайм
перестанет его касаться.

Проверка: `free -h` показывает своп, `df -h` < 85%.

### Этап 6 — перенос Supabase (переписан)

Исходный runbook предлагал `pg_dump -Fc -d <база>` и `pg_restore --no-owner`.
Для self-hosted Supabase **этого недостаточно**: состояние стека — это не только
таблицы приложения, но и роли (`anon`, `authenticated`, `service_role`,
`supabase_admin`, …), расширения (`vector` для `match_products`, FTS-конфигурация
для `search_products`), схема `storage` с каталогом объектов, и — отдельно —
сами файлы на диске. `--no-owner` снимает владельцев ролей, и после такого
восстановления PostgREST отвечает на запросы правами не тех ролей.

Правильный порядок:

**6.1. Одинаковые версии.** На новом сервере поднять Supabase из **того же
образа постгреса**, что на старом (снято в этапе 1, п.5). Разные мажорные версии
— значит только через дамп, и тогда `pg_dumpall --globals-only` обязателен.

**6.2. Ключи.** До первого запуска прописать в новом сервисе те же `JWT_SECRET`,
`ANON_KEY`, `SERVICE_ROLE_KEY`. Если их сгенерировать заново, ключ
`SUPABASE_SERVICE_ROLE_KEY` в приложении перестанет подходить, и всё встанет
ровно в момент переключения.

**6.3. Репетиция, без остановки прода.**

```bash
# логическая копия — она же страховка, которую надо скачать локально
docker exec <supabase-db> pg_dumpall -U postgres --globals-only > /tmp/goo-globals.sql
docker exec <supabase-db> pg_dump -U postgres -Fc -d postgres > /tmp/goo-test.dump
ls -lh /tmp/goo-globals.sql /tmp/goo-test.dump
scp /tmp/goo-globals.sql /tmp/goo-test.dump root@10.0.0.X:/tmp/
```

Восстановить на новом сервере в отдельную базу, сверить количество таблиц и
контрольные числа. Ориентиры, снятые с прода 21.08.2026:
